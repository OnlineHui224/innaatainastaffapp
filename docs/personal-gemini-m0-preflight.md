## 0. Research method and its limits — read this before trusting anything below

The brief said: *"Do NOT use forum posts, blogs, StackOverflow or memory as
architectural authority."* That constraint was honoured, and it cost coverage.

**The network egress proxy in this environment blocks direct page fetches to
`ai.google.dev`, `developers.google.com`, `docs.cloud.google.com` and
`supabase.com`.** Every attempt returned `EGRESS_BLOCKED`.

What did work is domain-restricted web search limited to those same official
domains, which returns search-engine extracts *of* the official pages. That is
one step weaker than reading the page: it is genuine official-doc content, but it
is not a verbatim quotation of the full page and it cannot show me the parts of a
page nobody indexed.

So every finding below carries one of three grades:

| Grade | Meaning |
|---|---|
| **VERIFIED** | Stated in official-doc content returned by domain-restricted search, unambiguous, and consistent across more than one official page. |
| **PARTIAL** | Official-doc content supports it, but a detail material to our design was not visible. Safe to design around; must be confirmed before M1 code depends on it. |
| **UNVERIFIED** | Could not be confirmed from official documentation in this environment. **Not designed around as fact.** Listed in Section 20. |

Nothing in this report is graded from memory. Where I know an answer but could not
confirm it officially, it is marked UNVERIFIED and the design offers a fallback.

## 1. Verified official technical findings

### 1.1 Google OAuth 2.0 endpoints

| Item | Value | Grade |
|---|---|---|
| Authorization endpoint | `https://accounts.google.com/o/oauth2/v2/auth` | VERIFIED |
| Token endpoint (code exchange **and** refresh) | `https://oauth2.googleapis.com/token` | VERIFIED |
| Revocation endpoint | `https://oauth2.googleapis.com/revoke` | VERIFIED |

Revocation behaviour, VERIFIED: revoking an **access** token also revokes its
corresponding refresh token. HTTP 200 signals success.

### 1.2 Offline access and refresh tokens

- `access_type=offline` is what causes a refresh token to be issued. **VERIFIED**
- **The refresh token is only returned on the first authorization.** **VERIFIED**
  This is the single most consequential operational fact in the whole design. If
  we ever lose a stored refresh token, a plain re-authorization will *not*
  silently hand us a new one — the user must be sent back through consent with
  `prompt=consent` to force re-issue. Section 9 designs for this.
- Access tokens expire; the application uses the refresh token against the token
  endpoint to obtain a new one. **VERIFIED**

### 1.3 CSRF `state` and PKCE

- `state` must be *"a unique, non-guessable value generated by your
  application"*, and the application must *"confirm that the state received from
  Google matches the state sent in your authorization request."* **VERIFIED**
- PKCE `code_verifier`: high-entropy random string from the unreserved set
  `[A-Z] [a-z] [0-9] - . _ ~`, **minimum 43 and maximum 128 characters**; the
  transformed value is sent as `code_challenge`. **VERIFIED**
- **PARTIAL — and this matters.** The *"strongly recommended"* PKCE language I
  could retrieve sits in Google's **installed/native app** guidance. I could not
  retrieve an equivalent verbatim sentence from the *web server applications*
  page mandating or recommending PKCE for confidential web clients. Google's
  Best Practices page does separately recommend sender-constraining tokens with
  DPoP against theft and replay.
  **Design decision:** we implement PKCE (S256) regardless. It is supported at
  the same endpoints, costs almost nothing, and is defence in depth for the
  Section 5 flow, in which the authorization code transits the browser. We do not
  claim Google requires it of us.

### 1.4 Quota attribution — `x-goog-user-project`

- `x-goog-user-project` sets the **quota project** for a REST request.
  **VERIFIED**
- Using it requires the calling identity to hold the
  **`serviceusage.services.use`** IAM permission on the named project.
  **VERIFIED**
- That permission is contained in the predefined role
  **`roles/serviceusage.serviceUsageConsumer`** (Service Usage Consumer).
  **VERIFIED**
- The **Generative Language API (`generativelanguage.googleapis.com`)** must be

### 1.8 Supabase Vault

- Secrets are created with **`vault.create_secret()`**, which returns the UUID of

- Official guidance, **VERIFIED and quoted because the design turns on it**:

## 3. Current Supabase / Edge Function architecture (M0.2)

**Nothing in this section was altered.**

### 3.1 Migrations

18 files, `20260730160037_001_create_profiles.sql` … 
`20260804014440_018_flight_itineraries.sql.sql`. Next free number is **019**.

### 3.2 Established security conventions — M1 should follow these, not invent new ones

Migrations 010–014 are a dedicated security-hardening series, and they establish a
house pattern that the Personal Gemini work should simply adopt:

1. **RLS policies keyed on `auth.uid()`**, e.g.
   `USING (auth.uid() = id OR is_admin_or_higher())`.
2. **SECURITY DEFINER functions with explicit privilege triples**:
   ```sql
   REVOKE EXECUTE ON FUNCTION fn(...) FROM PUBLIC;
   REVOKE EXECUTE ON FUNCTION fn(...) FROM anon;
   GRANT  EXECUTE ON FUNCTION fn(...) TO authenticated;
   ```
   Migration 010's own notes record that granting `anon` EXECUTE on SECURITY
   DEFINER functions was treated as a defect and fixed: *"The `anon` role never
   gets EXECUTE on any SECURITY DEFINER function."*
3. **Explicit `REVOKE ALL ... FROM anon / authenticated`** on tables that must not
   be client-readable.
4. **Role predicates as functions**: `is_platform_owner()`,
   `is_super_admin_or_higher()`, `is_admin_or_higher()`, `can_manage_staff()`,
   `get_current_user_role()`.

### 3.3 Edge Functions

Two exist: `supabase/functions/admin-api/index.ts` and
`supabase/functions/generate-itinerary/index.ts`.

Both use the identical auth pattern, and it is the correct one:

```ts
const serviceRoleKey = Deno.env.get("SUPABASE_SERVICE_ROLE_KEY") ?? "";
const adminClient = createClient(supabaseUrl, serviceRoleKey, {
  auth: { autoRefreshToken: false, persistSession: false },
});
// ...
const authHeader = req.headers.get("Authorization") ?? "";
const { data: userData, error: userError } = await adminClient.auth.getUser(token);
```

The caller's identity is derived from the **verified JWT**, never from the request
body. `admin-api` then re-checks role membership server-side against
`permittedAdministratorRoles`. **This already satisfies security principles 9 and
10, and M1 must reuse it verbatim rather than inventing an alternative.**

One weakness worth noting for M1: both functions send
`Access-Control-Allow-Origin: "*"`. That is tolerable for JWT-authenticated
endpoints, but the OAuth-related functions should be pinned to the HajjERP origin.

### 3.4 `config.toml`

**Does not exist.** `supabase/config.toml` is absent from the repository.

This is a real gap for M1, because `verify_jwt` is configured there. Its absence
means the two existing functions run on the platform default (`verify_jwt = true`)

### 3.5 Vault

## 5. OAuth start / callback security design (M0.6, M0.7)

### 5.1 The design question the brief asked

*"Determine whether OAuth callback must be unauthenticated at the platform
gateway and then securely validated using the one-time OAuth state."*

There are two workable shapes. I recommend the second.

**Option A — Google redirects straight to an Edge Function.**
`redirect_uri` = the callback function's URL, which must run with
`verify_jwt = false`, because Google's redirect carries no HajjERP JWT. All trust
then rests on the one-time `state`. This is the textbook pattern and it is sound.
Its cost: it violates security principle 9 *literally* — one endpoint exists that
does not identify its caller from a verified Supabase session — and it requires
creating `config.toml` specifically to open a hole.

**Option B — RECOMMENDED — Google redirects to the SPA, which relays to an
authenticated function.**
`redirect_uri` = `https://<hajjerp-app>/oauth/google/callback`, a React route.
That route reads `code` and `state` from the query string, immediately strips them
from the URL with `history.replaceState`, and POSTs them to
`personal-gemini-oauth-complete` **with the staff member's Supabase JWT
attached**. Every Edge Function stays `verify_jwt = true`.

**Why Option B wins here:** it lets the server check *two independent things*
instead of one — that the `state` is valid **and** that the Supabase user
presenting it is the same user the `state` was issued to. A stolen or replayed
`state` is then useless to anyone but its original owner. It also keeps principle
9 absolute with no exceptions to explain, and needs no `verify_jwt = false`
anywhere.

**The trade-off, stated plainly:** the authorization code appears momentarily in
the browser URL, and could land in browser history if `replaceState` were to fail.
That code is single-use, short-lived, PKCE-bound, and worthless without the client
secret — which never leaves the server. The residual risk is materially smaller
than the risk of maintaining an unauthenticated public endpoint. We accept it.

### 5.2 `personal-gemini-oauth-start`

- **Caller:** authenticated staff member. **Auth:** JWT required.
- Resolve `user_id` via `auth.getUser(token)`. Never from the body.
- Generate `state`: 32 random bytes from `crypto.getRandomValues`, base64url.
- Generate `code_verifier`: 64 random bytes → base64url (within the verified
  43–128 character bound); `code_challenge = BASE64URL(SHA256(verifier))`,
  `code_challenge_method=S256`.
- Insert one row into `google_oauth_states` (Section 8.2). **Store only
  `sha256(state)`, not `state`** — so a database read alone cannot forge a
  callback. Store `code_verifier` server-side in that row; it never reaches the
  browser.
- **Output:** the authorization URL only. Never the client secret, never the
  verifier.

Authorization URL parameters:

```
https://accounts.google.com/o/oauth2/v2/auth
  ?client_id=<from Edge Function secret>
  &redirect_uri=<exact registered URI>
  &response_type=code
  &scope=<Section 4 result>
  &access_type=offline
  &state=<random>
  &code_challenge=<S256>
  &code_challenge_method=S256
  &include_granted_scopes=true
  &prompt=consent        # only when re-issuing a refresh token — see 5.4
```

### 5.3 `personal-gemini-oauth-complete`

- **Caller:** the SPA callback route. **Auth:** JWT required.
- Resolve `user_id` from the JWT.
- Look up the state row by `sha256(state)`. Reject — with a generic message and
  no detail leaked to the browser — if the row is **absent**, **already consumed**
  (`used_at IS NOT NULL`), **older than 10 minutes**, or **belongs to a different
  `user_id` than the JWT**. This satisfies principle 13's four rejection cases:
  expired, reused, mismatched, invalid.
- Mark the row consumed in the **same statement** that reads it
  (`UPDATE ... WHERE used_at IS NULL RETURNING *`), so a concurrent replay loses
  the race atomically rather than being caught by a check-then-act gap.
- Exchange the code at `https://oauth2.googleapis.com/token` with `client_id`,
  `client_secret` (Edge Function secret), `code`, `code_verifier`,
  `grant_type=authorization_code`, `redirect_uri`.
- Read `sub` and `email` from the returned `id_token`. **`sub` is the stable
  identity key**; email can change.
- If no `refresh_token` came back, that is the "already authorized once" case —
  restart with `prompt=consent` rather than storing a connection we cannot renew.
- Write the refresh token to Vault; write metadata (Section 8).
- **Output:** `{ status: 'google_connected_project_required' }`. No token, no
  code, no scope secret ever crosses back to the browser.

### 5.4 Handling "refresh token only on first authorization"

Because of the VERIFIED behaviour in 1.2, the start function must decide between
two modes:

- **First connect, or reconnect after disconnect** → `prompt=consent` to
  guarantee a refresh token.
- **Adding scopes to a live connection** → `include_granted_scopes=true` without
  forcing consent, keeping the existing stored refresh token.

### 5.5 Redirect URI requirements

Google matches the redirect URI **exactly**, so it must be registered
character-for-character in the Cloud Console, including scheme, host, port and
path, with no trailing-slash drift. Every distinct deployment origin
(production, and any preview origin we choose to support) needs its own
registered entry. **PARTIAL** — the exact-match rule is well established in the
web-server flow documentation, but I could not open the page to quote the current
wording on `http://localhost` exemptions, so Section 19 asks the product owner to
register production explicitly rather than relying on a localhost allowance.

## 6. Google Cloud Project verification design (M0.4, M0.8)

### 6.1 UX: manual Project ID entry is the right call

The brief proposed staff typing a Project ID rather than HajjERP enumerating
their projects. **This is technically sound and I recommend it**, for three
reasons:

1. **Least privilege.** Listing projects needs Cloud Resource Manager access
   across the user's whole Google estate. Typing one ID needs nothing extra.
2. **Least surprise.** A staff member who sees HajjERP enumerate every Cloud
   project they can touch — including unrelated employers' and clients' projects —
   will reasonably distrust it.
3. **It does not actually reduce error.** A picker would still need the same
   backend verification, because being able to *see* a project does not mean the
   Gemini path works in it.

We must be precise about **which** identifier. Google exposes three:

| Field | Example | Use |
|---|---|---|
| Project **name** | `My Personal Gemini` | display only, not unique |
| Project **number** | `123456789012` | numeric, accepted in some APIs |
| Project **ID** | `my-personal-gemini-project` | **canonical — this is what we store and send** |

The UI must ask for **Project ID**, show a concrete example, and explain where in
the Cloud Console to find it. Client-side we apply only a shape check
(6–30 characters, lowercase letters, digits and hyphens, starting with a letter);
**shape is not validity**, and the backend decides.

### 6.2 Cheapest non-destructive verification — preferred

`GET https://serviceusage.googleapis.com/v1/projects/{PROJECT_ID}/services/generativelanguage.googleapis.com`
with `Authorization: Bearer <staff access token>` and
`x-goog-user-project: {PROJECT_ID}`.

One read-only call answers all three questions we care about, and **spends zero
Gemini quota**:

| Outcome | Meaning |
|---|---|
| `200` with `"state": "ENABLED"` | Project exists, identity can use it, Gemini API is on. **Verified.** |
| `200` with `"state": "DISABLED"` | Project reachable, but the Generative Language API is off → tell staff to enable it. |
| `403` | Identity lacks `serviceusage.services.use` → tell staff they need Service Usage Consumer on this project. |
| `404` | No such project, or invisible to this identity → likely a typo in the ID. |

Requires `cloud-platform` scope. If Section 4's probe shows the narrow scope
suffices for Gemini, we must fall back to 6.3.

### 6.3 Fallback verification if `cloud-platform` is not requested

`GET https://generativelanguage.googleapis.com/v1beta/models`
with the staff bearer token and `x-goog-user-project: {PROJECT_ID}`.

Listing models is a metadata read — it generates no tokens and consumes no
generation quota — while still exercising the exact bearer-token + quota-project
path a real extraction uses. It is weaker only in that its error messages are less
specific than Service Usage's, so the guidance we can give staff is coarser.
**PARTIAL** — I could not confirm from official docs whether `models.list`
enforces `x-goog-user-project` as strictly as `generateContent` does. Resolve
during M1.0.

### 6.4 The trust rule

The Project ID the browser sends is **input, never fact**. It is stored in
`cloud_project_id` with `project_verified_at` left `NULL` until a verification
call succeeds. **Only a row with a non-null `project_verified_at` may be used to
populate `x-goog-user-project`.** The extraction function reads the project from
the database row — never from its own request body, and never from a browser
header. That is security principle 16, enforced structurally rather than by
convention.

Re-verification runs when: the project changes, a reconnect happens, a Gemini call
returns 403/429 attributable to the project, or `last_verified_at` is older than
24 hours.

## 7. Per-staff quota attribution design

```
Staff browser
   │  Supabase JWT  (identifies WHO)
   ▼
Edge Function  visa-gemini-extract
   │  1. auth.getUser(jwt)                → user_id           [never from body]
   │  2. SELECT ... WHERE user_id = $1    → verified project  [never from body]
   │     (reject unless project_verified_at IS NOT NULL)
   │  3. vault.decrypted_secrets          → refresh token     [service role only]
   │  4. POST oauth2.googleapis.com/token → access token      [in memory only]
   ▼
POST generativelanguage.googleapis.com/v1beta/models/<model>:generateContent
     Authorization: Bearer <staff access token>
     x-goog-user-project: <verified project id from step 2>
```

Two independent facts must both hold before a single request goes out: the
**identity** comes from a Google refresh token belonging to this staff member,
and the **quota project** comes from a database row this staff member verified.
Neither is influenceable by the browser.

**No company fallback exists anywhere in this path** (principle 15). If the staff
member's project is unverified or their token is dead, the request is refused with
an explanation. There is no shared key to fall back to, and no code path that
could reach one.

## 8. Proposed database metadata schema (M0.5 A–C)

**Not created. Proposal only.**

### 8.1 `public.staff_google_connections`

```sql
create table public.staff_google_connections (
  user_id                  uuid primary key
                             references auth.users(id) on delete cascade,

  -- Google identity. `sub` is the stable key; email is display only and can change.
  google_subject           text        not null,
  google_email             text        not null,
  granted_scopes           text[]      not null default '{}',

  -- Quota project. Canonical PROJECT ID, never name or number.
  cloud_project_id         text,
  project_verified_at      timestamptz,

  -- Backend-derived state machine value (Section 12). Never client-set.
  connection_status        text        not null
                             default 'not_configured',
  last_verified_at         timestamptz,
  last_error_code          text,        -- short code only, never provider detail

  -- Pointer to the Vault secret. A UUID, not a credential.
  refresh_token_secret_id  uuid,

  created_at               timestamptz not null default now(),
  updated_at               timestamptz not null default now(),

  constraint staff_google_connections_project_shape
    check (cloud_project_id is null
           or cloud_project_id ~ '^[a-z][a-z0-9-]{4,28}[a-z0-9]$'),

  -- A project may never be marked verified without being set.
  constraint staff_google_connections_verified_needs_project
    check (project_verified_at is null or cloud_project_id is not null),

  -- One Google identity per HajjERP staff member and vice versa.
  constraint staff_google_connections_subject_unique unique (google_subject)
);
```

Every column here is metadata a staff member could read about themselves without
harm. **No token, no code, no secret.** The one sensitive-looking column,
`refresh_token_secret_id`, is a pointer that is worthless without the privileges
in Section 10 — and it is still withheld from the client by Section 10.2.

The `google_subject` uniqueness constraint deliberately prevents two HajjERP staff
accounts binding the same Google identity, which would make quota attribution and
audit meaningless.

### 8.2 `public.google_oauth_states`

```sql
create table public.google_oauth_states (
  state_hash    text        primary key,     -- sha256(state); the raw value is never stored
  user_id       uuid        not null references auth.users(id) on delete cascade,
  code_verifier text        not null,        -- PKCE; server-side only, never sent to browser
  redirect_to   text,                        -- post-connect in-app return path, validated allowlist
  created_at    timestamptz not null default now(),
  expires_at    timestamptz not null default now() + interval '10 minutes',
  used_at       timestamptz
);

create index google_oauth_states_expiry on public.google_oauth_states (expires_at);
```

Storing only the hash means that even a full read of this table cannot produce a
usable `state`. `code_verifier` is short-lived (10 minutes, single use) and is not
itself a credential — it is useless without the matching authorization code — so
Vault storage would add cost without adding meaningful protection. It must still
be unreachable from any client role.

### 8.3 Relation between metadata row and encrypted secret

```
staff_google_connections.refresh_token_secret_id  ──►  vault.secrets.id
```

Deliberately **not** a foreign key: `vault.secrets` is not ours to constrain, and
a hard FK would couple our migration to Vault's internal schema. The relationship
is enforced instead by the trigger in Section 9.4, which guarantees no orphan can
outlive its row.

## 9. Proposed Vault / token storage design (M0.5 D–J)

### 9.1 Storage

The refresh token goes to Vault via `vault.create_secret()`, whose returned UUID
becomes `refresh_token_secret_id`. Deterministic naming
`google_refresh:<user_id>` gives the reconciliation job in 9.5 something to scan.

**Access tokens are never stored anywhere.** They live in an Edge Function local
variable for the duration of one request and are discarded. Storing a
one-hour-lived credential buys nothing and creates a second thing to protect.

### 9.2 Retrieval by an Edge Function

An Edge Function authenticated with the **service role key** reads
`vault.decrypted_secrets` for exactly one `id` — the one on the row it has already
resolved from the verified JWT. The order is not negotiable:

```
verified JWT → user_id → row → refresh_token_secret_id → decrypt one secret
```

There is no code path in which a browser-supplied value selects which secret is
decrypted. That is principles 7 and 8 made structural rather than procedural.

### 9.3 Rotation and replacement

Google may return a new refresh token on re-consent. On receipt:

- Row already has `refresh_token_secret_id` → `vault.update_secret(id, new)`,
  keeping the pointer stable so no window exists with a dangling reference.
- Row has none → `create_secret`, then write the pointer.

A refresh that returns `invalid_grant` — user revoked access in their Google
account, or the token was unused past Google's inactivity window — moves the row
to `RECONNECT_REQUIRED` and clears `project_verified_at`. **The Vault secret is
deleted at that point**: it is known-dead and keeping it only widens exposure.

### 9.4 Disconnect and orphan prevention (M0.5 G, I)

`personal-gemini-disconnect`:

1. `POST https://oauth2.googleapis.com/revoke` with the refresh token — a **best
   effort**: if Google returns non-200 we continue, because leaving our copy
   behind because Google was briefly unavailable is the worse outcome.
2. `DELETE FROM staff_google_connections WHERE user_id = <from JWT>`.
3. The trigger below deletes the Vault secret.

```sql
create or replace function public.cleanup_google_vault_secret()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  if old.refresh_token_secret_id is not null then
    delete from vault.secrets where id = old.refresh_token_secret_id;
  end if;
  return old;
end $$;

create trigger staff_google_connections_secret_cleanup
  after delete on public.staff_google_connections
  for each row execute function public.cleanup_google_vault_secret();
```

Because the table cascades from `auth.users`, this fires on staff account deletion
too — so deleting a user cannot silently strand their encrypted refresh token.

### 9.5 Reconciliation

A scheduled function, weekly:

- delete `vault.secrets` named `google_refresh:%` with no matching row
  (belt-and-braces behind the trigger);
- delete `google_oauth_states` rows where `expires_at < now()`.

### 9.6 Suspended or deactivated staff (M0.5 J)

Deactivation is reversible; token deletion is not. So:

- `profiles.is_active = false` → every Personal Gemini function refuses, at the
  same point it already checks role. Status reports `PROVIDER_UNAVAILABLE` with a
  message about the account, not about Google.
- The row and Vault secret are **retained**, so reactivation restores access
  without dragging the staff member back through Google consent.
- **Deletion** of the account cascades and destroys both, per 9.4.

### 9.7 What is never stored, anywhere

Authorization codes. Access tokens. The client secret (Edge Function secret only —
never a `VITE_` variable, never the database). Plaintext refresh tokens. Document
bytes. Extracted passport or visa data outside the existing reviewed-and-saved
path.

## 10. Proposed RLS / privilege design (M0.5 D, E)

### 10.1 Both new tables are closed to clients

```sql
alter table public.staff_google_connections enable row level security;
alter table public.google_oauth_states      enable row level security;

revoke all on public.staff_google_connections from anon, authenticated;
revoke all on public.google_oauth_states      from anon, authenticated;
```

**No `CREATE POLICY` for `anon` or `authenticated` on either table.** With RLS on
and no permissive policy, the browser reads nothing and writes nothing — even with
a valid session. The service role, used only inside Edge Functions, bypasses RLS
by design and is the sole accessor.

This is stricter than the repo's existing tables, and deliberately so: `pilgrims`
is operational data staff must query directly, whereas nothing in these two tables
is ever needed by the browser except through a function that has already applied
its own checks.

### 10.2 Two read paths, following the house SECURITY DEFINER convention

**Own connection —** returns a deliberately narrow column set. Note what is
absent: `refresh_token_secret_id`, `granted_scopes`, `google_subject`.

```sql
create or replace function public.get_my_google_connection()
returns table (
  google_email        text,
  cloud_project_id    text,
  connection_status   text,
  project_verified_at timestamptz,
  last_verified_at    timestamptz,
  last_error_code     text
)
language sql security definer set search_path = '' as $$
  select google_email, cloud_project_id, connection_status,
         project_verified_at, last_verified_at, last_error_code
  from public.staff_google_connections
  where user_id = auth.uid();
$$;

revoke execute on function public.get_my_google_connection() from public, anon;
grant  execute on function public.get_my_google_connection() to authenticated;
```

`where user_id = auth.uid()` inside a SECURITY DEFINER body is what makes
principle 8 unbreakable: the function takes **no arguments**, so there is no
parameter through which one staff member could name another. This is the same
shape as the existing `profiles_update_own` policy.

**Administrator readiness —** replaces the `DEMO_STAFF_READINESS` fixture:

```sql
create or replace function public.get_staff_google_readiness()
returns table (
  full_name         text,
  email             text,
  connection_status text,
  google_email      text,
  cloud_project_id  text,
  last_verified_at  timestamptz
)
language sql security definer set search_path = '' as $$
  select p.full_name, p.email,
         coalesce(c.connection_status, 'not_configured'),
         c.google_email, c.cloud_project_id, c.last_verified_at
  from public.profiles p
  left join public.staff_google_connections c on c.user_id = p.id
  where public.can_manage_staff();
$$;

revoke execute on function public.get_staff_google_readiness() from public, anon;
grant  execute on function public.get_staff_google_readiness() to authenticated;
```

`where public.can_manage_staff()` reuses the repo's own predicate, so this
inherits the existing RBAC rather than introducing a parallel notion of "admin".
An administrator sees **readiness, not capability**: no token, no pointer, nothing
that lets them act as a staff member against that staff member's Google account.

### 10.3 Vault privileges

`vault.decrypted_secrets` is granted to **no** client role. Given the official
guidance in 1.8 — anyone with access to the view has the decrypted secrets — the
only correct grant is none. Access is via the service role inside Edge Functions.

This is also why **`SECURITY DEFINER` functions must never be written to return
decrypted secret material**: a definer function bypasses the very privilege wall
this section builds. No function in this design reads `vault.decrypted_secrets`.

## 12. Real connection state machine (M0.9)

Backend-derived, computed **only** from database state plus verification results.
The client renders what `personal-gemini-status` says and computes nothing.

| State | Exact backend condition | AI extraction | User-facing action |
|---|---|---|---|
| `NOT_CONFIGURED` | No row for `user_id` | ✗ | "Connect your Google account" |
| `GOOGLE_CONNECTED_PROJECT_REQUIRED` | Row exists, Vault secret present, `cloud_project_id IS NULL` | ✗ | "Enter your Google Cloud Project ID" |
| `CHECKING` | A verify call is in flight | ✗ | Progress only; never a terminal state |
| `PROJECT_SETUP_REQUIRED` | Verify returned `api_not_enabled`, `no_service_usage_permission` or `project_not_found` | ✗ | Specific Google-side fix, named exactly |
| `CONNECTED` | **All seven conditions in 12.1 hold** | ✓ | None — show account, project, last verified |
| `RECONNECT_REQUIRED` | Refresh returned `invalid_grant`, or the Vault secret is missing | ✗ | "Reconnect your Google account" |
| `USAGE_UNAVAILABLE` | Last Gemini call returned 429 / quota exhausted for the project | ✗ | "Your project's Gemini quota is exhausted" — **never** offer a company fallback |
| `PROVIDER_UNAVAILABLE` | Google 5xx / timeout, **or** `profiles.is_active = false` | ✗ | "Temporarily unavailable" / account message |

### 12.1 `CONNECTED` means all seven, per the brief

1. A `staff_google_connections` row exists for this `user_id`.
2. `refresh_token_secret_id` is non-null and the Vault secret resolves.
3. A token refresh **succeeded** — proven, not assumed.
4. `cloud_project_id` is non-null and passed shape validation.
5. `project_verified_at` is non-null — the identity can designate the project for
   quota.
6. The Generative Language API was observed reachable/enabled under that project.
7. `last_verified_at` is within the freshness window (24 h), or a fresh check just
   passed.

**Anything less renders something other than Connected**, and the fake gate
`ready: state === 'connected'` is deleted outright. Its replacement is a
server-computed boolean that the browser cannot influence — and even if a
tampered client forced `ready = true`, `visa-gemini-extract` re-derives all seven
conditions server-side and refuses. **The client gate becomes a courtesy, not a
control.**

## 13. Visa extraction API contract (M0.10)

**Design only. Not implemented.**

`POST /functions/v1/visa-gemini-extract`

| Aspect | Specification |
|---|---|
| Caller | Authenticated staff member with an existing Visa-logging permission |
| Auth | JWT required; `user_id` from `getUser()`; `profiles.is_active` re-checked |
| Max size | **10 MB**, matching `UploadVisaCard.tsx:22` — enforced **server-side**, not merely client-side |
| MIME types | `application/pdf`, `image/jpeg`, `image/png` — matching `ACCEPTED_TYPES`, minus the redundant `image/jpg` |
| Body | `{ mimeType, dataBase64 }` — **no `userId`, no `projectId`, no model override.** Every one of those is resolved server-side (principles 10 and 16) |
| Precondition | Recompute all seven of 12.1. Any failure → `409` with the state; **no extraction is attempted** |
| Token | Refresh at `oauth2.googleapis.com/token`; access token in memory only |
| Project | `x-goog-user-project` from the verified row |
| Model | `Deno.env.get('GEMINI_MODEL')` with a documented stable default (Section 14) |
| Google call | `POST .../v1beta/models/<model>:generateContent`, PDF/image passed **inline** |
| Timeout | 45 s hard cap via `AbortController`; mapped to `PROVIDER_TIMEOUT` |
| Storage | **None.** No Files API upload, no bucket write, no database write of document bytes |
| Response | Structured fields plus per-field confidence **only** |
| DB writes | **None to `pilgrims`, none anywhere.** This function is a pure read-and-return |

### 13.1 Response JSON Schema

```json
{
  "type": "object",
  "properties": {
    "travellerName":  { "type": ["string", "null"] },
    "passportNumber": { "type": ["string", "null"] },
    "visaNumber":     { "type": ["string", "null"] },
    "nationality":    { "type": ["string", "null"] },
    "confidence": {
      "type": "object",
      "properties": {
        "travellerName":  { "type": "number" },
        "passportNumber": { "type": "number" },
        "visaNumber":     { "type": "number" },
        "nationality":    { "type": "number" }
      },
      "required": ["travellerName","passportNumber","visaNumber","nationality"]
    }
  },
  "required": ["travellerName","passportNumber","visaNumber","nationality","confidence"]
}
```

Every field is nullable **on purpose**. A model that cannot read a field must be
able to say so. Forcing a non-null string is precisely how a plausible-looking
fabricated passport number gets into an operational record.

### 13.2 Extraction prompt (draft)

> You are reading a scanned Saudi Hajj/Umrah visa document. Extract only what is
> literally printed. Return `null` for any field you cannot read with confidence —
> do not infer, complete, correct or translate. Do not guess a passport number
> from a partially legible one. Report confidence between 0 and 1 per field.

### 13.3 Server-side validation before responding

Structured output constrains shape, not truth. So before returning:

- passport number matches `^[A-Z0-9]{6,12}$` after trimming, else null with
  `needsReview`;
- nationality is a plausible short alphabetic string;
- any field with confidence below 0.75 is flagged `needsReview: true`;
- **no field is ever auto-accepted.**

### 13.4 The human-review boundary is unchanged

The function returns extraction results **and nothing else happens**. Every value
arrives in the existing Visa workflow as `AI Extracted`, and it is the officer's
per-field `Mark reviewed` that promotes it to `Staff Reviewed`. Typing is not
verification; editing clears review. Matching to a HajjERP pilgrim still happens
after identity review, still keys on passport number, still requires explicit
confirmation, and the save still refuses without a confirmed existing pilgrim.

**None of that logic moves into the Edge Function**, which is what the brief means
by *"The function must never save directly to `pilgrims`."* The only change to
`VisaLoggerPage.tsx` in M3 is that `handleExtract` stops refusing and starts
calling this endpoint. The workflow around it is untouched.

### 13.5 Logging redaction (principle 11)

Never logged: authorization codes, access tokens, refresh tokens, the client
secret, `dataBase64` or any fragment of it, extracted field values, full document
contents.

Logged: `user_id`, timestamp, mime type, byte size, model id, outcome code,
duration, HTTP status. That is enough to debug and to bill, and it contains no
personal data of the pilgrim.

Concretely, this means **no `catch (e) { console.error(e) }`** anywhere in these
functions — a thrown fetch error can carry a full request body including the
document. Errors must be narrowed to a code before they are logged.

## 14. Model recommendation and why

**Recommendation: make the model a server-side environment variable
`GEMINI_MODEL`, read once in `visa-gemini-extract`, with a stable pinned default
— and confirm the default against the official models page before M3 ships.**

Reasoning:

1. The brief requires a **stable** model, not a preview or experimental one. A
   pinned specific ID such as `gemini-3.6-flash` is described in official content
   as *"a specific stable model, which usually doesn't change and is recommended
   for most production apps"* — exactly the property we want. Aliases that track
   "latest" are the wrong choice here: an extraction prompt validated against one
   model should not silently change under an operational system handling passport
   data.
2. **I could not fully resolve 3.6 versus 3.7** in this environment (Section 1.7).
   Official pages exist for both, and the "latest model" page currently names 3.7
   Flash. Rather than guess, the env-var design means the decision is a
   configuration change, not a code change, and can be made in five minutes once
   the models page is readable.
3. Flash-class is right for this workload regardless of minor version: single-page
   visa documents, four fields, structured output, latency in front of a waiting
   officer. Pro-class capability is not needed and costs the staff member's own
   quota.
4. The default is set in **exactly one place** so there is no second literal to
   drift.

**What must not happen:** hard-coding a preview/experimental ID, or reading the
model from the request body, which would let a browser select a model against the
staff member's quota.

## 15. PDF / image privacy handling

Visa documents contain passport numbers, full names, nationality and photographs.
The design minimises their lifetime at every step:

| Stage | Handling |
|---|---|
| Browser | Existing `UploadVisaCard` behaviour; object URL revoked on clear |
| Transport | HTTPS to the Edge Function; base64 in the body, **never in a URL or query string** |
| Edge Function | Held in a local variable for one request; **never written to disk, bucket or table** |
| Google | Passed **inline** in the `generateContent` call |
| Files API | **Not used.** Inline avoids creating a persisted Google-side copy |
| Response | Only the four fields plus confidence cross back |
| After | The processing copy goes out of scope with the request |

**One request per upload. One structured response. Discard.**

Nothing in M0 or the proposed M1–M4 adds permanent passport or visa image
storage. If a future requirement needs a document retained, that is a separate
product decision with its own approval, not something that arrives as a side
effect of extraction.

## 16. Error mapping

| Condition | Detected as | State | Shown to staff | Logged |
|---|---|---|---|---|
| No connection | no row | `NOT_CONFIGURED` | "Connect your Google account to use AI extraction." | code |
| Consent cancelled | Google returns `error=access_denied` | `NOT_CONFIGURED` | "Google connection was cancelled." | code |
| State expired / replayed / mismatched | state row check | unchanged | "That connection link is no longer valid. Please try again." *(one generic message for all four cases)* | code + reason |
| Refresh rejected | `invalid_grant` | `RECONNECT_REQUIRED` | "Your Google connection has expired. Reconnect to continue." | code |
| Vault secret missing | pointer resolves to nothing | `RECONNECT_REQUIRED` | as above | **alert** — indicates a data-integrity fault |
| No project set | `cloud_project_id IS NULL` | `GOOGLE_CONNECTED_PROJECT_REQUIRED` | "Enter your Google Cloud Project ID." | — |
| Gemini API off | Service Usage `DISABLED` | `PROJECT_SETUP_REQUIRED` | "Enable the Generative Language API in project `<id>`." | code |
| Missing Service Usage permission | `403` | `PROJECT_SETUP_REQUIRED` | "Your Google account needs the Service Usage Consumer role on project `<id>`." | code |
| Project not found | `404` | `PROJECT_SETUP_REQUIRED` | "No Google Cloud project `<id>` is visible to this Google account. Check the Project ID." | code |
| Quota exhausted | `429` | `USAGE_UNAVAILABLE` | "Your project's Gemini quota is used up. Try again later or raise the limit in Google Cloud." | code |
| Google 5xx / timeout | status / abort | `PROVIDER_UNAVAILABLE` | "AI extraction is temporarily unavailable. You can enter the details manually." | code + status |
| Account deactivated | `is_active = false` | `PROVIDER_UNAVAILABLE` | "Your HajjERP account is not active." | code |
| Unreadable document | model returns all nulls | `CONNECTED` | "Nothing could be read from this document. Enter the details manually." | code |

Two rules run through the whole table. **Every failure has a manual path** — the
existing `Enter details manually` route is never removed, so a Google outage
degrades the Visa Logger rather than stopping it. And **no failure ever routes to
a company project**; `USAGE_UNAVAILABLE` says the staff member's quota is gone and
stops there (principle 15).

## 18. Rollback plan

**Database:**

```sql
drop trigger if exists staff_google_connections_secret_cleanup
  on public.staff_google_connections;
drop function if exists public.cleanup_google_vault_secret();
drop function if exists public.get_staff_google_readiness();
drop function if exists public.get_my_google_connection();
-- Deleting rows first lets the trigger reap Vault secrets; drop the trigger last
-- in practice, or delete secrets explicitly before dropping the table.
drop table if exists public.google_oauth_states;
drop table if exists public.staff_google_connections;
```

Two cautions. **Order matters**: dropping the table before deleting its rows
bypasses the cleanup trigger and strands Vault secrets — so either delete rows
first, or sweep `vault.secrets where name like 'google_refresh:%'` afterwards.
And **the Vault extension is not dropped**: it may be adopted by other features,
and dropping it is far more destructive than the problem any rollback is solving.

**Application:** every change is additive and behind the state machine. Reverting
the commits restores the UI-only prototype, because nothing in the existing Visa
or Flight workflow is rewritten to depend on the new backend — the Visa page's
only new dependency is that `handleExtract` calls an endpoint instead of refusing.

**Google side:** rollback does not revoke staff consent. If the feature is
withdrawn, the OAuth client should be disabled in the Cloud Console so tokens stop
refreshing, and staff can revoke HajjERP from their Google account permissions
page.

## 19. Google Cloud manual setup checklist for the product owner (M0.13)

This is what will eventually need doing by hand, in plain terms. **Nothing here
should be done yet** — it is here so you can see the scope of it before approving.

**Do not paste any secret into this chat. Do not commit any secret to GitHub.**
Every value below goes into Supabase's Edge Function secrets and nowhere else.

### Part 1 — The company's Google Cloud project (one-time, ~20 minutes)

This project hosts the **sign-in application** only. It does **not** pay for
Gemini — each staff member's own project does that.

1. Go to <https://console.cloud.google.com> and create a project, e.g.
   `hajjerp-oauth`.
2. Open **APIs & Services → OAuth consent screen**.
3. Choose the user type:
   - **Internal** — available only if Inna Ataina has Google Workspace. **Strongly
     preferred**: no Google review, no "unverified app" warning for staff.
   - **External** — works with ordinary Gmail accounts, but staff will see an
     "unverified app" screen, and there is a cap of 100 users until Google
     verifies the app. Fine for current headcount; worth knowing about.
4. Fill in: App name (e.g. "HajjERP"), support email, company domain, developer
   contact email.
5. Add the scopes we finalise in M1 (Section 4). **Do not add extra scopes.**
6. If you chose External and stay in "Testing", add each staff member's Google
   address to the test users list.

### Part 2 — The OAuth client (one-time, ~5 minutes)

7. **APIs & Services → Credentials → Create credentials → OAuth client ID**.
8. Application type: **Web application**. Name it "HajjERP Web".
9. Under **Authorised redirect URIs**, add the exact production URL we give you.
   It must match character for character — no trailing slash, correct `https`.
10. Google then shows a **Client ID** and a **Client secret**. Keep the tab open.

### Part 3 — Storing the two values (one-time, ~5 minutes)

11. In the Supabase dashboard: **Edge Functions → Secrets**.
12. Add `GOOGLE_OAUTH_CLIENT_ID` = the Client ID.
13. Add `GOOGLE_OAUTH_CLIENT_SECRET` = the Client secret.
14. Add `GOOGLE_OAUTH_REDIRECT_URI` = the same URI from step 9.
15. Add `GEMINI_MODEL` = the stable model ID confirmed in M3.

That is the whole company-side setup. The client secret exists in exactly one
place: Supabase Edge Function secrets. It is never in the React app, never in the
repository, never in the database, never in a `VITE_` variable, and never in a
message to me.

### Part 4 — What each staff member does themselves (~10 minutes each, once)

Each staff member needs their own Google Cloud project, because Gemini usage is
billed and rate-limited per project:

16. Create a Google Cloud project, or use one they already own.
17. Enable the **Generative Language API** in it.
18. Ensure their Google account has the **Service Usage Consumer** role on it.
19. Attach billing if they need more than the free tier.
20. Copy the **Project ID** — the hyphenated one like `my-gemini-project-2026`,
    **not** the display name and **not** the 12-digit number.
21. In HajjERP → My Account, click **Connect Google**, approve, then paste the
    Project ID.

HajjERP will verify it and tell them precisely which of steps 17–19 is missing if
verification fails. **HajjERP will never create a project, enable billing or grant
IAM roles on their behalf.**
